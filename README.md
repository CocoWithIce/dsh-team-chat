# dsh-team-chat

> 多角色团队群聊侧栏 — 把 DeepSeek Harness 的 AgentTeams 团队变成**能看、能说话、能对话**的团队前台。

一个 `dsh-better-sidebar` 标签页：成员在线状态、**成员的真实发言**、任务广播实时流入同一个对话流；每个角色有独立的**角色框**，任意消息可**引用回复**，回复以**飞书话题**式折叠展开。

```
┌─ 🤝 多角色协作群聊 · multi-role-team ─────────────┐
│ ● researcher 工作中  ● engineer 空闲  ● reviewer 空闲 │
├───────────────────────────────────────────────────┤
│ ┌───────────────────────────────────────────────┐ │
│ │ 🔬 researcher  [研究员]                 10:21 │ │  ← 角色框（左边框 = 角色色）
│ │ 我先核对字段，再给结论……                        │ │
│ │                        [回复]  [2 条回复 ▸]   │ │
│ └───────────────────────────────────────────────┘ │
│   ┌───────────────────────────────────────────┐   │
│   │ 🛠 engineer  [工程师]                  10:23 │   │  ← 话题内回复（缩进）
│   │ ↩ researcher：我先核对字段…                  │   │  ← 引用块（可点击跳转原消息）
│   │ 已按阈值实现，附运行证据                       │   │
│   │                        [回复]                │   │
│   └───────────────────────────────────────────┘   │
│ 📋 派发任务：分析项目结构                            │
├───────────────────────────────────────────────────┤
│ ↩ 回复 researcher：我先核对字段…              ✕   │  ← 引用输入态
│ [💬 全员 ▾]  [📋 派任务]                          │
│ [ 在回复该消息… ]                     [ 发送 ]     │
└───────────────────────────────────────────────────┘
```

## 它解决什么

AgentTeams 默认是**任务卡片**式的：任务列表、审批计划、状态快照。
但多角色协作真正好用的形态是**群聊**——谁在干活、谁说了什么、任务怎么被拆开的，应该像刷群一样一眼看到，而且能**对着某句话继续追问**。

这个插件做三件事：

1. **把团队变成群聊**：成员的真实发言、工作状态、任务流转，全部实时流入一个对话流
2. **把新会话交给团队**：团队功能开启时，新会话的任务优先由常驻「铁三角」接手
3. **像飞书一样对话**：角色框区分发言者，可引用回复，回复折叠成话题、按需展开

## 安装

```bash
dsh plugin --profile <你的 profile 名> add dsh-team-chat
```

插件通过 `dsh.bundle.patch` 自动挂载，无需手改 profile 文件。

**前置条件**

| 依赖 | 必需性 | 说明 |
|---|---|---|
| AgentTeams 插件（`@nanmicoder/dsh-agent-teams`） | 功能必需 | 提供团队引擎；插件只依赖其子代理标签约定 |
| 存在活动团队 | 运行时 | 无团队时侧栏显示「未发现团队成员」 |
| `dsh-better-sidebar` | 可选 | 有则注册为它的标签页；无则自动使用右侧常驻栏 |

> **加载顺序无关**：客户端不假设 better-sidebar 已经就绪——先直接解析一次，未果则用 `ctx.inject(['betterSidebar'], …)` 等它出现。即使本插件先加载，标签页仍会注册；注册成功的一刻右侧常驻栏自动让位，两个表面不会同时存在。

## 功能

### 1. 新会话优先路由到团队

在 **设置 → 团队群聊** 打开「启用团队功能」后，每次新开会话都会注入一段路由提示词，让队长 agent：

- 若本会话还没有团队 → 先用 `agent_teams_create` 建立团队，再逐个 `agent_teams_add_member` 建立**铁三角**
- 把用户任务优先拆解为任务 DAG 分派给团队，自己只做拆解/分派/裁定/汇报
- 仅在用户给出**实际任务**时建队——寒暄、致谢、纯问答不建队

> **为什么是提示词层而不是服务层**：`agentTeams` 服务注册在队长 Agent 自己的作用域里，兄弟插件 `ctx.get('agentTeams')` 得到的是 `undefined`，无法替 agent 建队。而队长 agent 本身持有 `agent_teams_*` 工具，因此路由通过提示词完成。这是经过实测确认的约束，不是取巧。

路由段**按 agent 作用域注册**（`agentPresets.serviceFor(agent, 'systemPrompt')`），所以团队成员（独立 agent 作用域）不会收到队长指令；若该机制不可用，自动退化为全局注册 + 文本自排除条款。

> **实测修正（v0.3.2）**：只有 agent 的 preset 组合**自己挂载了 `systemPrompt`** 时才有作用域实例——`serviceForAgent` 会 `standingMountFor(agent.ctx)` 找不到就返回 `undefined`（`@deepseek-ai/dsh-agent-presets` 的 `mount.js:242`）。默认 preset（如 `cordis`）用的是宿主那一份，因此作用域注册会全部失败。
> 现在的做法是**双层**：① 始终注册一个**全局基线**段（AgentTeams 自己用的就是这条路径），保证任何部署下路由都生效；② 额外尝试按 agent 作用域注册（先试 preset 实例，再试 `agent.ctx.systemPrompt`），成功则**同名遮蔽**全局段，使该会话可用自己的团队。
> 代价：既然基线是全局的，团队成员也会收到它——因此文案第 6 条明确要求子代理忽略本节。

**可选增强：把铁三角固化为 AgentTeams profile**

上面的路由提示词按角色名逐个建队。如果你希望三角色连同执行提示词、评审策略一起固定下来，可以在 profile 的 AgentTeams 插件行加一个 `trio` profile：

```yaml
- id: agent-teams
  config:
    profiles:
      trio:
        description: 常驻铁三角：调研 / 实施 / 把关
        taskPlanning: captain
        members:
          - name: researcher
            role: 研究员
          - name: engineer
            role: 工程师
          - name: reviewer
            role: 审查员
        reviewPolicy:
          requiredReviewers: [reviewer]
          codeMaxRounds: 2
```

之后提示词里的建队步骤可以直接用 `agent_teams_create(profile='trio')`。本插件不强制这一步——没有 profile 时按角色名逐个建队同样可用。

### 2. 角色框

每条发言渲染为独立卡片：**左边框颜色 = 角色色**，头部含角色图标、名称、角色标签、时间。

| 角色 | 图标 | 标签 | 颜色 |
|---|---|---|---|
| researcher | 🔬 | 研究员 | `#4f8cff` |
| engineer | 🛠 | 工程师 | `#34c77b` |
| reviewer | 🧐 | 审查员 | `#ff9f43` |
| 我 | 🙋 | 我 | `#a78bfa` |

系统提示（成员开工/空闲）、任务广播、成员收到的指令保持轻量行样式，避免淹没对话。

### 3. 引用回复

任意消息的「回复」按钮进入引用输入态（输入框上方显示 `↩ 回复 X：……`），发送后：

- 回复挂在被引用的消息下，正文上方显示**引用块**（点击可滚动定位原消息并高亮）
- 该成员的下一条发言自动落入同一话题（一次性绑定，10 分钟过期）

> 绑定是**启发式**：一条被引用的投递 → 该成员的下一条发言归属该话题。绑定失败只影响归属，不影响消息送达。

### 4. 话题展开（飞书话题式）

话题根默认折叠，显示 `2 条回复 ▸`；点击展开后回复以缩进轨道渲染（每条仍是完整角色框，可继续回复）。折叠状态下有新增回复时计数加粗。

### 5. 团队模板：多团队 + 每成员配置

**设置 → 团队群聊** 就是一个团队模板库：

- **多个团队**：新建 / 复制 / 删除；每个团队有自己的成员名册
- **每成员可配**：名称、角色、provider/model、推理强度、**Skills、MCP、依赖插件、Memory、Soul（人格）、执行指引**
- **默认团队**：标记任意团队为默认，新会话自动使用
- **会话内切换**：群聊侧栏顶部的团队下拉可临时切换本会话使用的团队（下一条提示词立即生效）
- **预览**：成员编辑器里点「预览将写入 persona 的执行指引」，直接看到最终进入成员 system prompt 的文本

#### 每成员配置如何真正生效（重要）

AgentTeams 派生成员时，persona 模板由它自己生成，**唯一的外部注入点是 `executionPrompt`**：

```js
// @nanmicoder/dsh-agent-teams lib/members.js:425
- Execution guidance:
  ${executionPrompt}      ← 本插件渲染的全部成员配置都汇入这里
```

所以本插件的做法是：把你填写的 Soul / Skills / MCP / 插件 / Memory / 执行指引渲染成一段结构化文本，作为该成员的 `executionPrompt` 传给 `agent_teams_add_member`，最终出现在成员的 system prompt 里：

```
【角色人格】先取证再结论；区分「已验证」与「推测」…
【优先技能】understand、code-review（动手前先用 skill 工具加载）
【可用 MCP】postgres（只读）
【依赖插件】dsh-better-sidebar
【记忆】team:multi-role-team；开工前查、收工后写
<执行指引原文>
```

#### 能力边界（如实说明）

| 能力 | 是否每成员硬隔离 | 说明 |
|---|---|---|
| 名称 / 角色 / provider / model / 推理强度 | ✅ 平台强制 | AgentTeams 原生支持，直接写入成员创建参数 |
| Skills / MCP / 插件 / Memory / Soul / 执行指引 | ⚠️ **指引级**（模型须遵守） | 经 `executionPrompt` 进入成员 persona；模型会遵循，但不是工具层拦截 |
| 工具级白/黑名单 | ❌ 当前不可用 | AgentTeams 的 `toolFilter` 由其内部固定（仅拒绝队长专属工具） |

「指引级」意味着：成员会按配置行事，但它**技术上仍能**调用未列出的 skill 或 MCP。若你需要真正的硬隔离（例如「审查员只能读不能写」），见下方「后续计划」。

### 6. IM 会话的团队进度同步

当会话来自 IM（飞书 / 企业微信等，用户消息里带 `<dsh_im_source>`），团队进度要能被 IM 用户看到。本插件提供**两条互补通道**：

| 通道 | 开关 | 机制 | 覆盖范围 |
|---|---|---|---|
| **A. 队长回复播报** | 「IM 会话播报团队进度」（默认开） | 路由提示词要求队长把成员进度写进回复；IM 插件把**该轮回复**转发到聊天 | 队长被成员汇报唤醒后产生的总结 |
| **B. 浏览器主动投递** | 「主动推送团队进度到 IM」（默认**关**） | 宿主从会话首条用户消息解析出 IM 来源（`botId` + `targetId`），浏览器半边把成员开工/空闲、任务创建/完成等简短进度**直接投递**到该会话 | 成员级逐条进度 |

通道 A 的局限（实测得出）：IM 插件是**按「被 IM 消息触发的那个 turn」**转发回复的——它跟踪一个具体 turn 号，而成员汇报唤醒的是新 turn，因此这类轮次不会被自动转发。通道 B 正是为此而做。

**通道 B 的实现要点**：IM 插件的主动投递端点是

```
POST /api/dsh-im/delivery/messages
{ "botId": "bot_…", "targetId": "group:oc_…:thread:omt_…", "text": "…" }   ← 必须恰好这三个键
```

该路由受部署请求围栏保护（`isTrustedApiRequest` → 浏览器鉴权），**宿主侧调用一律 403**（实测即使对齐 Origin 头也过不去，同进程拿不到浏览器 cookie）。因此投递由**浏览器半边**发起（它持有凭据），宿主只负责解析 IM 来源并通过 `/state` 暴露 `im: { botId, targetId }`。

投递失败会以提示形式显示在群聊面板里（例如 `IM 投递失败：delivery-failed`），不会静默失败。

### 7. 持久化与作用域

| 配置 | 存放位置 | 作用域 |
|---|---|---|
| 开关 + 团队模板 + 默认团队 | `team-chat` 设置命名空间（DSH 设置文件） | 全局 |
| 会话内团队切换 | 宿主内存（`Map<sessionId, teamId>`） | 单会话，重启回落默认团队 |

## 工作原理

### 数据通路（关键设计）

AgentTeams 的 `agentTeams` 服务**注册在队长 Agent 自己的作用域内**，兄弟插件拿不到。但团队成员是**队长会话的持久化 continuable 子代理**，且每个都带着
`agent-teams:<团队名>:<成员名>` 的子代理标签。于是：

| 需求 | 数据源 |
|---|---|
| 成员名册 + 实时活动 | `ctx.subagents.listChildren(captainSessionId)` |
| 成员的真实发言 | `ctx.sessionQuery.readSurface(memberSessionId)` |
| 发言 / 派任务（唤醒成员） | `ctx.subagents.sendMessage(captainAgent, …)` |

队长会话通过「哪个 Agent 拥有带 `agent-teams:` 标签的子节点」自动发现，不依赖任何硬编码 id。

### 会话隔离

每个会话拥有自己的团队，因此状态按**队长会话 id** 分区。`/state` 接受 `?sessionId=`，客户端从 better-sidebar 的 `TabComponentProps.scope.sessionId` 透传；若该会话本身是成员会话，自动回落到其父会话。

### 前后端分工

```
  浏览器 (lib/client.js)                    Host (lib/index.js)
  ┌──────────────────────┐                 ┌──────────────────────────────┐
  │ better-sidebar 标签页 │──GET /state────▶│ 轮询成员会话 (3s)             │
  │ 角色框 / 引用 / 话题   │◀──threads──────│ 增量提取 (seq 游标) → 话题组装 │
  │                      │──POST /speak───▶│ 绑定话题 + subagents.sendMessage│
  │ 设置页 (settings.     │──POST /task────▶│ 广播任务给全员                 │
  │  section)            │──GET/POST──────▶│ 读写 team-chat 设置命名空间    │
  │                      │   /settings    │                               │
  └──────────────────────┘                 └──────────────────────────────┘
```

**线程组装在 Host 完成**（`groupThreads`），客户端只渲染——分组逻辑因此可被单元测试覆盖，且不会在两半边出现两份实现。

Host 半边暴露六个路由（`/plugins/dsh-team-chat/{state,speak,task,settings}`），每个都**重新校验 Connection 鉴权围栏**——原始 WebServer 路由不继承该保护，缺失时返回 503 而不是把团队状态暴露出去。

### 增量读取

每个成员维护 `seq` 游标：首次见到成员时设为会话尾部（面板打开即干净，不回放历史），之后只提取新增事件，且从尾部反向扫描、最多 24 条即停，避免长会话（数万事件）被反复全量扫描。

## 已知限制

- **每成员配置是指引级，不是工具级隔离**：Skills / MCP / 插件 / Memory / Soul 都经 `executionPrompt` 进入成员 persona，模型会遵守，但技术上仍可调用未列出的工具。硬隔离需要 AgentTeams 支持在成员创建时挂载不同 agent preset，或使用下述的委托 provider 方案。
- **冷恢复边界**：向当前处于 `inactive`（非活跃）的成员投递消息时，子代理的冷恢复可能失败，界面如实显示错误而不静默丢弃。成员被唤醒过一次后即可正常收发。
- **话题绑定是启发式**：见「引用回复」一节；不宣称精确关联。
- **面板「派任务」是广播**：成员各自判断是否接手，不写入 AgentTeams 正式任务板与质量门禁。需要正式任务契约时仍由队长在对话里创建。
- **常驻栏模式无会话隔离**：右侧常驻栏（未装 better-sidebar 时）拿不到当前会话 id，回退为「第一个发现的团队」。
- **会话内团队切换不持久**：存于宿主内存，应用重启后回落到默认团队；默认团队本身是持久设置。
- **会话内切换对提示词的影响视部署而定**：只有该 agent 能承载作用域注册时，切换才会改变其路由提示词；否则提示词一律使用**默认团队**，切换仅影响群聊侧栏显示哪个团队的名册。
- 内容上限：单条发言 1200 字符、单成员执行指引 1200 字符、每团队 8 名成员（与 AgentTeams `maxMembers` 默认一致），内存保留最近 400 条消息、面板展示最近 200 条。
- 团队 id 与成员名采用保守白名单（小写字母、数字、`-`、`_`），因为它们会进入子代理标签 `agent-teams:<team>:<member>` 与状态目录名。
